# 开仓与止损卡：多用户产品重构规格

日期：2026-10-16。

Status: ready-for-agent

**规格状态：**根据已确认讨论整理，测试边界已由用户确认；业务代码尚未重构。

**发布状态：**已发布到本仓库的本地 Markdown issue tracker，状态为 `ready-for-agent`；本文件是规格正文的维护入口。尚未开始业务实现，也未发布到远程平台。

## Problem Statement

现有工具能够帮助单个使用者生成开仓方案、只读核验 Binance 账户、查看资产并整理交易复盘，但登录、凭据、浏览器状态和后台任务都围绕单人本地服务设计。其他人无法自行注册并安全接入各自的账户，使用者也缺少公开官网作为产品入口。

直接将现有应用搬到普通 Serverless 请求中会破坏长期账本、后台归档、分段 AI 分析和较大数据传输。只增加用户表也无法解决私有响应串用、旧本单失效、跨用户备份恢复和注销后数据被旧快照恢复的问题。

使用者需要一个可公开访问、支持多用户独立使用的产品，同时保留现有开仓与复盘能力、精度、数据、手机交互和风险约束。重构不能以丢失原始证据、放宽风险限制、减少分析范围或悄然增加模型费用为代价。

## Solution

建设公开官网和邮箱注册、验证、登录入口。每位产品用户同时拥有一个活跃 Binance 绑定，使用专用只读凭据连接自己的账户；平台加密托管 Binance 与用户自备模型密钥，并将用户数据、账户历史、浏览器状态和任务严格隔离。

用户继续在 Binance 手动执行交易。本产品提供开仓方案、查询时点核验、资产快照、订单与完整交易复盘、笔记、统计、行情、AI 分析及导出恢复。AI 费用由用户向其模型服务商承担，调用次数不限，通过公平排队控制并发。

Next.js 提供官网、用户页面和认证，常驻 Node 业务服务处理交易规则、Binance 调度、任务及大数据传输，Neon PostgreSQL 长期保存状态。旧数据通过演练、对账和短暂停写迁移；注销和灾备恢复具有明确的数据清理及凭据失效边界。

## User Stories

1. 作为访客，我希望无需登录即可阅读公开官网，以便了解产品提供的开仓、只读核验和交易复盘能力。
2. 作为访客，我希望官网正文可以被搜索引擎读取，而个人交易页面受到访问保护，以便找到产品而不暴露用户资料。
3. 作为新用户，我希望通过邮箱和密码公开注册，以便独立使用产品而无需部署自己的应用服务。
4. 作为新用户，我希望完成邮箱验证后再进入私有业务，以便确认登录身份对应我能接收邮件的邮箱。
5. 作为待验证用户，我希望邮件发送失败后能够受限流保护地重发，以便恢复注册流程而不重复创建账号。
6. 作为产品用户，我希望能够登录、退出、找回及重置密码，以便持续访问自己的工具和记录。
7. 作为产品用户，我希望能够撤销其他设备的会话，以便停止不再需要的访问。
8. 作为尚未绑定账户的已验证用户，我希望能够进入绑定和模型设置，以便完成首次使用配置。
9. 作为产品用户，我希望登录、依赖服务或权限异常得到明确反馈，以便区分会话失效与暂时不可用。
10. 作为产品用户，我希望提交专用 Binance 只读凭据并由后端验证权限，以便使用真实数据且不向平台授予交易、提现或划转权限。
11. 作为产品用户，我希望平台使用 Binance 返回的稳定 UID 确认账户，以便更换 API Key 时仍能找到原有历史。
12. 作为产品用户，我希望同一 Binance UID 只能属于一个产品用户，以便我的笔记和交易历史不会被另一个账号取得。
13. 作为产品用户，我希望同时只启用一个 Binance 账户，以便明确当前开仓、核验和同步的账户范围。
14. 作为产品用户，我希望更换同一账户的密钥时保留原记录，以便轮换凭据而不丢失方案和复盘历史。
15. 作为产品用户，我希望绑定不同 UID 时创建独立历史，以便新账户不会继承或改写旧账户的资料。
16. 作为产品用户，我希望绑定失败或只读权限无法确认时保留已有数据，以便失败的连接尝试不会破坏原账本。
17. 作为产品用户，我希望凭据加密保存且不回显，以便后续使用时不用反复输入，同时避免密钥泄露到页面或日志。
18. 作为产品用户，我希望浏览器只在提交期间处理密钥且不持久保存，以便共享设备不会留下可被下一位用户读取的凭据。
19. 作为产品用户，我希望输入后立即看到草稿，并在正式生成前读取最新必要数据，以便区分预演参数和可供本次手动执行的开仓方案。
20. 作为产品用户，我希望按亏损预算、入场方式和止损计划计算仓位，以便沿用现有风险约束准备交易。
21. 作为产品用户，我希望生成后固定本单亏损预算与绝对止损，以便后续核验不会悄然扩大可接受风险。
22. 作为产品用户，我希望单层和双层止损都按全部仓位在最终止损退出确定初始数量，以便近端退出假设不会放大仓位。
23. 作为产品用户，我希望资金不足时按交易步长缩量而不放宽预算或止损，以便方案仍符合原约束。
24. 作为产品用户，我希望金额和数量保持现有十进制精度与取整规则，以便框架和数据库迁移不改变计算结果。
25. 作为产品用户，我希望继续使用市价、GTC 限价及部分成交核验，以便覆盖原有手动开仓流程。
26. 作为产品用户，我希望清楚区分预估强平价、当前强平价及强平缓冲，以便不把估算或历史查询当成持续保证。
27. 作为产品用户，我希望账户、行情或规则缺失、过期、不一致时不出现有效方案或通过状态，以便及时处理不可靠的数据。
28. 作为产品用户，我希望在 Binance 自行下单、撤单及设置账户，以便平台始终保持只读执行边界。
29. 作为产品用户，我希望回到网页后按实际成交、成本和有效止损重新核验，以便判断查询时点的持仓是否符合原方案。
30. 作为产品用户，我希望修改输入、离开页面、断网或查询失败时撤销旧通过状态，以便不会误用已失效结果。
31. 作为产品用户，我希望刷新、重登和服务重启后能恢复原本单并重新查询，以便已有持仓不需要重新生成更宽松的计划。
32. 作为原工具使用者，我希望迁移中的当前本单经过原凭证验证后保留预算和绝对止损，以便在新产品中继续可信核验。
33. 作为产品用户，我希望保留自己的偏好、止损模板和本单输入，以便减少重复填写且不与其他用户混用。
34. 作为手机用户，我希望复制、键盘、焦点、窄屏展示及切换 Binance App 返回的行为保持可用，以便继续原有手机操作流程。
35. 作为产品用户，我希望账户资产页保留资产与查询信息，并在每轮完成后等待 30 秒刷新，以便知道数据的时点与更新状态。
36. 作为产品用户，我希望开仓摘要维持现有 3 秒更新，并在限流时清楚显示冷却，以便不会把停更误认为最新状态。
37. 作为产品用户，我希望历史归档不会占满开仓和核验所需的读取能力，以便正在进行的前台操作得到优先处理。
38. 作为产品用户，我希望真实与模拟数据始终明确区分，以便模拟结果不会被当成真实账户核验。
39. 作为产品用户，我希望订单列表按一行一张订单展示执行状态和已实现盈亏，以便查看与交易所记录一致的事实。
40. 作为产品用户，我希望完整交易按从空仓到再次空仓的周期归并，以便加减仓和分批退出不会放大统计样本。
41. 作为产品用户，我希望订单与完整交易保持关联，并正确表达反手及双向历史，以便追溯同一成交对不同周期的归属。
42. 作为产品用户，我希望日期筛选、显示、统计和导出继续使用北京时间，以便重构前后的时间口径一致。
43. 作为产品用户，我希望保留筛选、分页、详情链接和浏览器返回状态，以便在列表与单笔复盘之间继续工作。
44. 作为产品用户，我希望费用、资金费或成交链缺失时显示待确认和已知分项，以便不把不完整记录误判为零盈亏或完整结果。
45. 作为产品用户，我希望首次及后续历史取数都由我主动触发，以便进入页面、恢复联网或返回网页不会擅自访问 Binance。
46. 作为产品用户，我希望复用已知订单下载任务和已完成分页，以便失败恢复不会重复消耗下载额度。
47. 作为产品用户，我希望查询不到的旧历史与未发现范围保持明确缺口，以便不会误以为账本已经涵盖全部历史。
48. 作为产品用户，我希望能查看原始证据并比较原方案与实际执行，以便有依据地区分事实、关联不明及计划偏离。
49. 作为产品用户，我希望记录复盘笔记和交易风格标签，并在页内导航时保留未保存草稿，以便持续整理个人判断。
50. 作为产品用户，我希望并发笔记更新和恢复冲突不会静默覆盖新版本，以便保留双方记录并明确处理差异。
51. 作为产品用户，我希望统计覆盖当前筛选的全部范围，并列出有效及排除样本，以便页面分页不会改变表现结论。
52. 作为产品用户，我希望保留合约价与标记价行情、交易事件及原止损证据，以便按明确来源和时间范围复盘。
53. 作为产品用户，我希望较大的报告、行情和证据仍能完整取得，以便传输限制不会导致静默截断或抽样。
54. 作为产品用户，我希望提供自己的模型 Key 并直接承担模型服务商费用，以便平台无需替我垫付或经营充值套餐。
55. 作为产品用户，我希望模型 Key 长期加密托管且可替换或撤销，以便支持离开页面后的任务及以后主动重试。
56. 作为没有有效模型 Key 的用户，我希望仍能使用非 AI 功能和查看旧报告，以便模型连接问题不妨碍整理交易。
57. 作为产品用户，我希望 AI 分析只在主动发起时调用模型，以便查看页面、归档或新成交不会自动产生模型费用。
58. 作为产品用户，我希望自主决定本次是否发送已保存笔记，以便控制个人自述进入模型的范围。
59. 作为产品用户，我希望分析开始时冻结交易、行情、统计和允许发送的笔记，以便之后新增数据不改变运行中的依据。
60. 作为产品用户，我希望超出模型容量时分段处理全部证据再综合，以便不会因容量限制遗漏交易或把摘要当原始证据。

66. 作为产品用户，我希望模型 Key 改变后剩余分析暂停，待我明确继续才使用新 Key，以便不会静默更换付费身份。

70. 作为产品用户，我希望恢复在预览仍有效时原子完成、失败时保留原账本，以便并发变化不会让旧预览覆盖新数据。

73. 作为产品用户，我希望解绑后撤销凭据、停止相关任务，并保留自己的只读历史与 UID 占位，以便断开连接不等于遗失记录。
74. 作为产品用户，我希望归档账户仍可查看和导出，重绑同 UID 后恢复正常功能，以便历史与当前活跃账户清楚分开。
75. 作为产品用户，我希望 Key 临时失效只暂停对应外部能力，以便不会无故失去本地笔记等仍可用功能。

77. 作为产品用户，我希望平台灾备最长 30 天到期，恢复旧库时重新执行删除和撤销决定，以便注销后的资料和凭据不会重新生效。
78. 作为新绑定同 UID 的用户，我希望不继承前一位已注销用户的数据，也不被其旧删除记录误伤，以便新的账户归属独立成立。
79. 作为共享设备的用户，我希望登出、跨标签退出和账号切换立即隐藏原用户数据，以便缓存、本单和草稿不会被下一位用户看见。
80. 作为原工具使用者，我希望先演练和对账再短暂停写切换，并明确新写入后的回退限制，以便迁移失败不会丢失新记录。
81. 作为产品维护者，我希望沿用现有业务测试并补充多用户、数据库和恢复验收，以便重构不会用“新页面可打开”代替完整交付。
82. 作为产品维护者，我希望先完成本地实现，再按明确地区、预算和真实链路证据上线，以便小规模试运行的资源与能力可核实。

## Implementation Decisions

1. **产品与执行边界。** 首版提供公开官网、邮箱密码注册和邮箱验证。普通用户不获得运营权限。Binance 只使用后端固定白名单 GET；下单、撤单及其他账户操作由用户在 Binance 执行，不为解决读取失败扩大权限。
2. **工程与部署。** 一个代码库、一个 package、两个运行入口。Next.js 与 React 负责网页和认证，网页目标部署 Vercel；一个常驻 Node 业务服务负责交易规则、凭据使用、账本、任务和数据传输，数据目标 Neon PostgreSQL。首版不用独立队列产品、对象存储或 Sentry。
3. **身份与模块所有权。** Better Auth 为唯一登录源，认证和资料模块拥有自己的写入职责；交易账本和外部调用由业务服务拥有。Next 不绕过业务服务直接修改交易数据，也不持有用户凭据解密主密钥。
4. **受保护的数据访问。** Next 经有效会话签发面向业务服务的短期受限委托凭据。业务服务每次读取当前会话、用户状态、授权代次及资源归属；凭据内的旧状态不能绕过撤销。浏览器只在内存持有凭据，经请求头发送，跨源仅允许精确来源，Cookie 不扩大到其他主机。
5. **归属模型。** 产品用户、Binance UID、不可复用的账户归属实例和凭据版本分别表达。每用户最多一个活跃绑定；活跃和归档记录保留 UID 独占占位。并发绑定由数据库唯一约束及事务裁决，不能只靠前端校验或先查后写。
6. **首次绑定与凭据更新。** 服务端用提交的凭据验证读取权限、拒绝写权限并读取稳定 UID 后建立关系。同 UID 换 Key 保留账本并更新授权代次；不同 UID 建立新作用域，不改写旧历史身份。失败不丢弃已有数据，也不泄露其他用户身份。
7. **凭据托管。** Binance 和模型 Key 均长期采用标准认证加密，密文与所属用户、用途和版本绑定，主密钥独立保管。凭据不回显，不进入浏览器持久化、普通日志或用户下载备份；受控平台灾备可含密文。密钥轮换和恢复独立于登录密码及认证 Secret。
8. **状态与生命周期。** 解绑撤销凭据和相关执行权，账本转为原用户只读归档，允许查看与导出，禁止新增笔记、AI、同步或恢复写入。同 UID 重新验证绑定后恢复正常功能。活跃绑定的 Key 临时失效仅停止对应外部能力，不能等同于解绑。
9. **注销与 UID 释放。** 注销要求最近重新认证并先提供导出机会；确认后立即停用登录、凭据与新任务，后台清理在线数据，完成后才释放 UID。清理覆盖交易、笔记旧版本、冻结分析快照、报告、临时文件和私有缓存；后来同 UID 的新绑定使用新的归属实例。
10. **删除与恢复控制记录。** 删除和凭据撤销决定在向用户确认成功前可靠落地，并有不随业务库恢复点回退的持久记录。恢复先隔离、禁止用户访问及外部调用，按原用户、归属实例和版本重放决定，更新恢复代次。记录不完整时保持关闭，不以 UID 为唯一删除条件。
11. **保留期限。** 平台持有的灾备、旧库、演练库、迁移导出和临时副本最长 30 天到期，不能因称作迁移留档而绕开清理。独立控制记录仅保留恢复安全所需身份与代次，并覆盖所有仍可恢复副本及恢复验证过程；用户自己下载保管的备份不在平台控制范围内。
12. **账本与精度。** PostgreSQL 承接交易、证据、方案、核验、原始历史、同步状态、归档进度、标签、笔记、行情、分析和旧版本十二类记录。金额与数量保持无损字符串和共享 BigInt 计算，不经浮点中转；保留现有费用、反手分配、交易周期及缺口规则。
13. **风险与可信本单。** 复用共享计算、按最终止损确定数量和固定原预算/绝对止损的规则。方案、草稿、历史事实和查询时点核验分别表达。已有持仓不能通过重新生成更宽松方案绕过恢复或核验，缺 UID 的旧凭证不能补造历史身份。
14. **Binance 协调。** 出口 IP 权重与冷却共享，签名、私有请求去重、缓存和权限错误按产品用户、绑定及凭据版本隔离。前台生成与核验优先于后台归档；滚动交接不能重置冷却或同时启动多个无协调的出口调度者。
15. **刷新与手动触发。** 开仓摘要保持 3 秒、资产页保持每轮完成后 30 秒；严格生成和核验不复用过期观察缓存。复盘外部取数仅主动触发，列表按原有进入、筛选、分页等规则读取；网络恢复、窗口聚焦和任务完成不引入额外自动刷新。
16. **任务执行。** 任务持久化发起用户、账户与凭据版本、冻结证据、执行版本、租约和检查点。原子领取执行权，同账户归档串行，AI 按用户公平排队并控制并发；不限次数不等于不限并发。正常关闭页面和登出不取消已接受任务，停用、解绑、撤销及取消阻止后续未授权调用和迟到写入。
17. **AI 行为。** 首版沿用当前已支持的 DeepSeek 模型与推理配置，不新增任意用户自定义模型 URL，也不提供公共付费 Key 回退。单笔及最多 100 笔筛选范围分析冻结全量证据，按容量分段后综合；笔记需用户允许。失败不自动重放可能收费的请求，更换 Key 后仅在用户明确继续时使用新版本。
18. **大数据传输。** 任务提交和进度返回摘要，历史任务分页，报告及原始证据按需取得；统计保持全筛选范围。可能较大的 JSON、导出和 64 MiB 恢复使用受保护 Node 直连，不通过 Next 再包装超限载荷。分块与分页不改变分析覆盖，文件 UID 不构成上传或恢复授权。
19. **备份协议。** 新备份采用带产品用户、不可复用归属实例及服务端证明的 v2 封装，保留原有业务内容、预览、补缺和个人记录冲突处理。恢复检查当前归属和删除状态，预览变化拒绝写入，事务失败全量回滚。旧 v1 只经受控迁移转换，不作为注销后凭 UID 跨归属恢复的通道；备份内容不构成可信当前本单。
20. **前端迁移。** Vue 页面逐模块迁往 React，保留现有视觉、手机交互、业务页面 URL、筛选详情状态、北京时间及原生语义。新公开首页与受保护工作台分别承载公开内容和个人功能。认证、绑定、模型设置、安全及注销页面补足多用户流程。
21. **浏览器隔离。** 用户资料及首次绑定按产品用户隔离，账户数据额外按来源、归属实例及代次隔离。本单、模板、偏好、草稿和 Query 缓存先确认身份再加载；退出和身份变化清除可见私有状态，迟到响应检查当前身份代次。旧无归属浏览器数据只能由原用户明确迁移。
22. **安全与观测。** 生产保持强制 CSP、输入校验、来源与 CSRF 保护；日志只记录必要错误类别、时延、请求标识和版本，不采集凭据、交易内容、笔记或模型输入。认证页之外的业务和密钥输入也受相同保护，首版不加入第三方追踪或会话录制。
23. **旧数据切换。** 先隔离演练、明确原拥有者并逐类对账，再短暂停写迁移，不长期双写。旧本单在原环境验签后通过受控通道迁入，旧登录密码和验签配置不长期上云。没有可信身份或签名时先在旧工具完成本单，再允许该账户切换。
24. **回退边界。** 新系统开放写入前可撤销切换；首次需要保留的新写入后，旧 SQLite 仅供只读对账。后续优先回滚到兼容当前 PostgreSQL 的应用版本或进入维护状态，保全新增记录、删除及撤销决定，不直接恢复可写旧库。
25. **实施与上线顺序。** 依次完成基线和身份入口、归属/密钥/账本、业务执行与数据通道、React 页面及官网、迁移恢复演练与完整本地交付，再进行获授权的外部验证与试运行。具体依赖 patch、供应商、地区及参数通过兼容性检查与实际预算确定，不将设计稿当实测证据。

## Testing Decisions

用户已确认：以对外业务 HTTP 行为为主要测试边界，沿用现有 transport 替换 Binance 和模型响应；辅以 PostgreSQL 真实事务测试、手机浏览器验收及共享金额计算边界测试。

1. **什么是有效测试。** 从用户或调用者可观察的输入、返回值、访问拒绝、持久结果和外部请求次数判断行为；不锁定私有函数、内部 Map、组件树或 ORM 调用方式。框架与存储迁移后，同一业务断言应继续成立。
2. **主测试边界。** 通过生产业务 HTTP 入口启动应用，验证认证、绑定、方案、核验、账户、账本、任务和恢复。外部服务沿用可替换 transport，数据库使用隔离 PostgreSQL；避免为每个内部类新增专属测试接口。
3. **身份与安全。** 使用至少两个合成产品用户，覆盖注册验证、未绑定设置、停用、登出、会话撤销、伪造委托凭据、越权资源 ID、同 UID 并发绑定、密钥更新及跨来源写请求。以实际响应、授权结果和缺失的外部调用证明拒绝生效。
4. **账户与调度。** 模拟不同用户同时访问相同上游 URL，检查各自请求签名和返回数据，验证共享出口冷却、前台优先、权限错误隔离及严格核验不使用旧观察结果。现有账户读取、刷新协调和归档 HTTP 测试作为先例。
5. **金额和领域计算。** 保留共享纯计算入口的独立边界测试，覆盖最终止损定量、资金不足缩量、交易步长、长金额和小数、风险方向取整、反手费用尾差及缺失证据。这是高价值的窄边界，不拆开算法内部步骤测试。
6. **数据库行为。** 通过账本公开接口或 HTTP 并发操作，检验唯一绑定、笔记版本、过期恢复预览、冲突旧版本、全量回滚及稳定隔离。使用真实 PostgreSQL 的约束和事务，不以 SQLite 或内存替身通过宣称目标数据库兼容。
7. **后台任务。** 模拟用户离开、普通登出、取消、Key 撤销/替换、进程中断及两个执行实例交接；检查可见任务状态、已完成分段和外部请求次数。证明不会重复领取或自动重放未知收费请求，导入的历史任务不会自行执行。
8. **传输和恢复。** 使用超过 4.5 MB 的合成 AI、统计与证据响应及接近 64 MiB 边界的恢复输入，验证受保护直连、完整性和过期/越权授权拒绝。测试 v2 归属验证、已注销旧包拒绝、受控 v1 转换，不能只检查小样本下载成功。
9. **生命周期与灾备。** 验证归档只读、临时 Key 失效与解绑不同、在线删除覆盖旧版本和冻结快照、清理完成后释放 UID，以及新归属不继承旧资料。恢复模拟包括独立控制记录丢失、删除/撤销重放、旧代次全部失效和同 UID 后来绑定不被误删；保留期限使用可控时钟验证，再在上线环境确认实际配置。
10. **浏览器验收。** 沿用 Playwright 的生产构建浏览器边界，覆盖 Chromium 和 WebKit、320px/390px/1280px、键盘焦点、复制、返回、草稿及隐藏/禁用状态。检查两用户与跨标签退出后的可见内容，保持刷新频率、复盘手动读取、北京时间、公开 HTML 与 CSP。
11. **迁移工具。** 使用合成旧库、旧浏览器数据与恢复凭证，从工具的输入、报告和目标账本结果验证。比较身份、金额字符串、净盈亏、方案关联、笔记版本及缺口，覆盖无可信 UID/签名的拒绝以及新写入前后不同的回退边界；不将生产旧库当测试夹具。
12. **既有测试先例与完整交付。** 继续使用现有 Node 内置测试、断言、HTTP fixture、可替换外部响应及浏览器模拟服务器。先记录原版本基线，迁移后完成类型、lint、格式、生产构建、业务测试和浏览器检查；只在有具体缺口时增加组件测试工具。
13. **外部证据分层。** 自动测试、模拟浏览器、实体手机和真实 Neon/Binance/模型联调分别记录，互不替代。真实权限、出口、数据库恢复、30 天保留和模型费用行为必须在获授权环境验证，不能由本地配置存在推断通过。

## Out of Scope

- 自动下单、撤单、交易设置、提现、划转、自动行情推荐及改变现有开仓风险算法。
- 首版同时激活多个 Binance 账户、多个产品用户共享同一 UID、组织团队或通用运营权限平台。
- OAuth、SSO、原生移动客户端、对外开放 API、CMS、平台充值、套餐、订阅及模型计费系统。
- 任意模型供应商或用户自定义请求地址；首版保留当前模型支持范围。
- 无人值守自动交易、自动重放可能收费的 AI 请求，以及超出现行规则的自动外部取数和推送。
- Sentry、第三方行为追踪、会话录制、独立队列产品、对象存储、Kubernetes 或通用微服务拆分。
- 与等价迁移无关的视觉重设计、无关文件重排或为统一工具而重写全部测试。
- 长期 SQLite/PostgreSQL 双写、首次新写入后直接恢复可写旧库、把无可信归属的旧备份自动挂给新账号。
- 在本规格发布过程中安装依赖、编写产品代码、采购云资源、调用真实模型或账户、迁移真实数据以及生产部署。
