# 开仓与止损卡：多用户产品重构方案

**方案 A｜Next.js 全栈 + Vercel + Neon**

**文档版本：1.3｜日期：2026-10-16｜状态：架构审查完成；票据 01 已完成本地验收，其余模块待实施**

> 本文是三轮范围确认及最终审查后的目标架构，执行顺序与交付条件集中在[重构实施计划](refactor-implementation-plan.md)。用户已确认产品、账户生命周期、凭据托管和部署分工；计划仍待最终确认，地区、预算及具体云资源在上线前确定。票据 01 的依赖、身份入口与本地合成验收见[项目现状](status.md)；尚未创建云资源或进行真实链路、性能验收。性能、容量、限流和恢复指标是工程初始目标，不代表平台保证或实测结果。

## 1. 需求、假设与边界

### 1.1 已确认需求

2026-10-16 三轮审查确认，决策依据见 [ADR 0006](adr/0006-multi-user-product-migration.md)、[ADR 0007](adr/0007-account-binding-and-credentials.md) 与 [ADR 0008](adr/0008-persistent-business-service.md)：

- 产品从个人工具扩展为公开官网与多用户注册，用户绑定各自 Binance 账户。官网保留公开内容与 SEO 目标。
- Next.js、Vercel、Neon 为目标选型，允许按业务需要保留常驻后端或任务执行服务，不要求所有业务在普通请求函数内执行。
- 现有功能、历史数据、未完成本单恢复、手机交互与北京时间口径按等价迁移验收。用户与账户隔离是新增要求，现有单用户代码不因此自动满足。
- Binance 固定白名单只读接入、用户手动交易、固定预算与绝对止损、共享 BigInt 计算及查询时点核验语义继续保留。
- 每个产品用户同时只有一个活跃 Binance 绑定，同一 UID 的归属独占；同 UID 换密钥保留历史，换 UID 不转移旧数据。解绑撤销凭据，保留原用户的只读历史和 UID 占位；注销在线数据清理完成后释放占位，新绑定不继承旧数据。
- Binance 与用户自备模型 Key 均长期加密托管，不回显，不进入浏览器持久化、日志或用户下载的业务备份；平台受控灾备允许密文，加密主密钥单独保管。注销立即停用登录和凭据，清理全部在线副本，平台灾备最长 30 天到期，恢复时重放删除及撤销决定。
- 公开注册，首版只提供邮箱与密码登录，要求邮箱验证。
- AI 使用用户自备模型密钥，费用由用户向模型服务商承担；保留不限调用次数，通过排队控制并发，首版不做平台充值、套餐及计费。更换 Key 后未完成任务由用户明确继续，不能静默换 Key 扣费。
- 一个常驻 Node 业务服务承接 Binance 读取、核验、账本、归档、AI 和大数据传输；Next.js 承担网页与认证，Neon 保存状态。首版不增加独立队列产品或对象存储，不接入 Sentry。
- 旧库通过短暂停写切换，先演练与对账，不长期双写；旧本单单独验签迁移。旧 SQLite 保留为只读依据，产生新系统写入后不能直接恢复为可写旧服务。
- 先按小规模试运行；用户地区、具体人数和基础设施月预算暂不确定，继续设计与本地验证，上线选址及资源采购前再确定。

当前实现仍为 Vue/Vite、常驻 Node 后端与 SQLite 账本；功能地图及实际验收状态分别见[项目索引](index.md)和[项目现状](status.md)。以下方案必须覆盖这些已存在的业务，不能按空白官网项目实施。

### 1.2 本文采用的默认假设

- 主要用户地区与运行预算保持待定，不能从原通用方案的“海外用户”假设推出部署区域或默认月支出。
- “用户后台”包含该用户的开仓与核验、账户资产、交易记录与复盘，以及新增账户绑定、个人资料与安全设置。运营后台 `/admin` 为可选扩展，普通注册用户绝不自动获得运营权限。
- 第三方 OAuth、SSO、团队组织、订阅支付与移动端 API 不纳入首版；公开注册和邮箱验证按第 1.1 节执行。
- 官网内容由代码仓库维护，页面数量有限，没有已确认的 CMS 编辑流程。
- 新加坡仅作为候选主区域，选址还需验证 Binance 只读链路、出口限制及用户访问情况；应用与数据库靠近部署不代表交易所链路已通过。
- 未提供并发量、数据规模和预算，方案不声称能支持某个固定用户数。通过负载测试与监控决定扩容。

### 1.3 第一版明确不做

不预置 NestJS、Kubernetes、通用微服务体系、全站动态 SSR 或通用权限配置平台。现有归档、AI 分析、跨请求 Binance 读取协调及大文件备份恢复都属于一期迁移范围；任务执行和文件传输的必要设施须据此选择，不能以“未来扩展”为由省略。

### 1.4 等价迁移的业务契约

| 范围           | 必须承接的行为与依据                                                                                                                                                                                |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 开仓与核验     | 保留草稿、正式方案、查询时点核验的区别；固定原预算和绝对止损，沿用共享 BigInt、精度与交易步长；覆盖迁移前生成、迁移后恢复的本单。见[产品决策](product-spec.md)与[实现说明](entry-implementation.md) |
| 账户资产与读取 | 开仓摘要 3 秒、资产页每轮完成后 30 秒；保留查询时点、前台优先、共享限流与冷却，正式生成及核验继续按严格读取边界执行。见[账户规格](account-snapshot-spec.md)                                         |
| 交易记录与复盘 | 保留订单与完整交易两种记录、筛选统计、笔记、行情、分析、CSV 与备份恢复；北京时间及手动外部取数语义不变。见[复盘规格](trade-review-spec.md)                                                          |
| 后台任务       | 已存在的归档和单笔/批量 AI 分析须支持离开页面后继续、取消及明确中断；用户主动继续/重试的语义不变。部署方案要处理跨实例执行权、重复执行与取消，不能仅迁移任务状态表                                  |
| 数据迁移       | 列明所有 SQLite 业务记录、来源与稳定 UID、方案关联、笔记版本及恢复事务；保留旧库并做结果对账。现有 JSON v1 恢复会重置部分同步/任务状态，不能直接称为状态无损迁移                                    |
| 浏览器身份隔离 | 保留原有功能与恢复体验，并增加产品用户与 Binance 账户作用域；当前本单、偏好、模板、草稿、请求和缓存不得被下一位登录用户读取，旧无归属本地数据不能默认归给下一位用户                                 |
| 验收           | 以现有业务测试和手机交互为回归基线，补充多用户越权、多实例任务、PostgreSQL 并发与数据迁移验收；新官网与认证通过不能替代旧功能验收。见[开发与验证](development.md)                                   |

现行生产 CSP 已强制执行，迁移不能把 Report-Only 当成同等保护；首版仅用平台/服务端最小日志。64 MiB 恢复及可能较大的 AI、统计和证据响应通过受保护业务数据通道传输，不能静默缩减范围以满足 Vercel 普通函数体积限制。[^R32]

### 1.5 审查结论与上线前条件

未发现需要继续追加产品选择的关键问题。已确认分支全部纳入本文；最终审查补齐大 JSON 传输、不可复用的归属实例、恢复点之外的删除/撤销记录，以及旧库可回切窗口等工程约束，详见[实施计划](refactor-implementation-plan.md)。

地区、预算和具体主机由用户暂缓确定，作为上线条件保留；本地工程、合成数据和模拟验证不依赖现在选定云供应商。计划的最终确认授权本地重构，不等同于采购、实际账本迁移或生产部署授权。

## 3. 总体架构与部署拓扑

```text
浏览器 / 搜索引擎
    │ HTTPS
    ▼
Vercel / Next.js（区域待定）
    ├── 公开官网与静态资源
    ├── Better Auth、资料 / 设置 ──→ Neon：认证、用户设置
    └── 受保护网页 / 小请求入口 ──→ 常驻 Node 业务服务
浏览器 ── 短期受限授权的数据直连 ──→        │
                                        ├── Binance 固定白名单只读
                                        ├── 用户 Key 的模型调用
                                        └── Neon：绑定、账本、任务、密文凭据

解密主密钥：仅授权业务服务使用，独立保管
删除 / 撤销控制记录：不随上述业务库恢复点一起回退
事务邮件：Next 认证模块 → EmailService → Resend
错误监控：平台及服务端最小日志，无 Sentry
发布：GitHub Actions → 迁移 → 网页与业务服务候选 → 验证 → 切换
```

Vercel 的全球网络并不意味着业务数据库在全球多地可写。本方案的动态业务采用单主区域，应用函数靠近数据库运行，公开静态内容由平台缓存分发。Vercel 官方建议函数尽量靠近数据源；Neon 与 Vercel 均提供新加坡区域。[^R01]

正式部署时需要显式设置函数区域，不能依赖平台默认区域。也不要因为客户分布全球，就把依赖单区域数据库的所有函数无差别铺到多个区域。

### 3.1 小规模试运行的部署分工

采用一个常驻 Node 业务服务承接 Binance 读取协调、开仓核验、账本业务写入、历史归档、AI 排队和大数据处理；Next.js 负责网页、认证及受保护的调用入口，Neon 保存业务状态。沿用现有模块边界，先不增加 Redis、独立队列产品、对象存储或多个业务微服务。

业务服务仍须核对可信调用身份、用户状态和账户所有权，不能信任浏览器提供的 userId/UID，也不能因请求来自 Next 就跳过资源授权。Next 中的认证/资料模块与业务服务分别拥有自己的写入职责；服务端组件通过经授权的业务入口获取数据，不跨服务直写同一套交易表。

普通短请求可通过网页同源入口；64 MiB 恢复、大导出及可能较大的 JSON 使用浏览器到常驻服务的受保护数据通道，避免经过普通 Vercel Function 或被 SSR/RSC 再包回同样大响应。当前分析接口返回包含全量快照的任务，统计与详情也可能包含无界证据；改为任务摘要、历史分页及按需取得报告/原始证据，完整分析和统计范围不变，禁止静默截断。

Better Auth 是唯一登录源。Next 经当前会话签发面向业务服务的短期委托凭据，绑定原会话、用户、允许操作及必要账户作用域；业务服务每次检查当前会话/用户状态、授权代次与资源归属，不能只相信凭据内的旧状态。浏览器只在内存持有委托凭据，经请求头发送，不放 URL 或持久存储；跨源仅允许精确来源，Cookie 仍限定网页主机。登出撤销页面数据访问，不取消此前已接受的后台任务。

文件授权额外限制大小和使用范围，服务端重新验证所有权；上传声明 UID 不是授权。凭据输入通过受保护通道交给业务服务，用户 Key 的解密能力及主密钥只授予业务服务，Next 构建/网页环境不持有解密能力。实现时验证大于 4.5 MB 的合成任务、统计/证据及 64 MiB 恢复；具体主机、域名和代理超时在上线前验证。

### 3.2 Binance 读取协调的多用户边界

现有 `src/account-refresh.ts` 的协调器同时持有单套凭据、额度、缓存和队列，私有请求的去重键不含用户身份，不能直接供所有用户共用。目标须分别处理：按出口 IP 共享请求权重与 429/418 冷却；按产品用户、绑定、凭据版本隔离签名、私有响应去重、缓存及权限错误。前台生成/核验优先于历史归档，排队后重新签名时仍使用原账户作用域。

Binance USDT 合约官方说明将请求权重和相关封禁按 IP 统计；具体下载等端点另有额度时，按其端点规则处理，不将全部上游限制归为用户配额。部署及滚动交接时只允许一个有效出口调度者，或提供等价的共享原子预算，不能因新实例启动将冷却清零。[^R34]

### 3.3 任务状态与凭据版本

排队控制并发，不新增每日或总调用次数配额。任务保存发起用户、账户作用域、冻结证据、绑定/凭据版本、执行版本与检查点；按用户公平调度，并限制全局及每用户并发，数值在模拟负载验证后配置。同一账户的归档串行，已有分页、分段与下载任务 ID 继续复用。

领取执行权须用数据库原子条件更新和有效租约。重启只判定失去执行权的任务中断，不能像当前单进程构造函数一样将所有 running 记录改成中断；新实例不能重放结果未知的收费请求。关闭页面或普通登出不取消已授权任务，保持现有行为；用户停用、绑定/密钥撤销和主动取消须阻止新外部请求，并以执行版本阻止越权迟到写入。

模型 Key 更新后，不静默用另一套 Key 继续扣费；暂停剩余步骤，由用户明确选择新凭据继续。已发出的请求仍可能产生费用，保留尝试及未知用量语义。恢复、解绑、注销等维护操作须与同账户任务写入互斥，取消本进程 AbortController 不能代替数据库中的失效标记。各绑定状态的允许操作见第 10.5 节。

## 4. 技术栈与版本策略

| 类别             | 选型                                                | 使用约定                                                               |
| ---------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| 语言             | TypeScript                                          | `strict`，运行时校验不能由类型声明替代                                 |
| 运行时           | Node.js 24 LTS 主线                                 | 本地、CI、Vercel 使用同一主版本                                        |
| Web 框架         | Next.js 16.4 主线 + App Router                      | 实施时锁定已修补稳定 patch；不采用 canary                              |
| React            | 与 Next.js 基线匹配的 React 19 系列                 | `react` 与 `react-dom` 版本一致，验证 Ant Design 兼容性                |
| 缓存模型         | Cache Components                                    | 只显式缓存公开数据；不混用旧版本路由缓存配置                           |
| 包管理           | pnpm                                                | 锁定 packageManager，提交 lockfile，CI frozen install                  |
| UI               | Ant Design + CSS Modules                            | 官网品牌化样式；后台组件库按路由隔离                                   |
| 表单             | Ant Design Form + 服务端 Zod                        | 不额外叠加另一套表单状态库                                             |
| 客户端服务端状态 | TanStack Query                                      | 列表、筛选、分页、mutation 和失效刷新                                  |
| 认证             | Better Auth + Prisma Adapter                        | 只启用当前需要的认证能力                                               |
| 数据库           | Neon PostgreSQL；本地 PostgreSQL 同一主版本         | 建议以 PostgreSQL 17 作为一致性基线，不表示它是最新主版本              |
| ORM              | Prisma ORM 7 工作流 + `@prisma/adapter-pg`          | 本文的 schema、generate、migrate 命令均按 7.x 文档，不混用新主版本命令 |
| 邮件             | Resend                                              | 仅服务端调用；开发测试使用 fake adapter 或收件人白名单                 |
| 测试             | 现有 node:test + Playwright，补 PostgreSQL 集成测试 | 复用已有业务断言，组件工具仅按实际需要增加                             |
| 监控             | 平台 / 服务端最小日志，无 Sentry                    | 统一 requestId 和 release 标识，禁止凭据和交易内容采集                 |
| CI/CD            | GitHub Actions + Vercel CLI/API                     | 单一编排入口，生产受保护环境审批                                       |

截至文档日期，官方已发布 Next.js 16.4，并为新项目推荐 Cache Components；Vercel 当前支持 Node.js 24。以上是本方案的版本基线，不代表已经运行过这组依赖的集成测试。实施第一步必须完成认证、Prisma、Ant Design 首屏样式和构建兼容性验证。[^R02]

选择 Prisma 7 工作流是为了明确这份方案的目录和迁移语义。升级 ORM 主版本属于独立变更，应同步更新认证适配器、生成器与 CI 命令，不能仅修改 package.json。[^R03]

价格页、产品页、文章页只在真实内容存在时增加，不先制造大量空的 SEO 页面。运营后台 `/admin` 不属于默认交付范围。

### 5.2 首页策略

根布局不读取 Cookie、Session 或用户资料。官网主体文案、标题、链接和必要图片描述进入初始 HTML。首页右上角的“登录 / 进入控制台 / 用户菜单”使用独立客户端小组件读取会话，失败时不影响公开内容展示。

根布局不挂载 Ant Design、后台 QueryClient 或全局用户 Provider。路由组 `(marketing)`、`(auth)`、`(console)` 不改变 URL，它们用于组织各自布局与依赖。

在所选 Next.js 版本中，为 marketing 路由组添加静态输出约束并在构建中验证；不要将静态约束放在全站根布局而阻止后台请求时逻辑。Next.js 16.4 提供确保静态输出的相关能力，实施时按该版本文档使用。[^R02]

### 5.3 后台策略

后台入口在服务端确认身份与访问权限，然后返回不含敏感字段的用户 DTO。布局检查用于导航体验；真正的数据读取与修改仍在业务入口再次授权。不能把“布局已经校验过”作为接口省略鉴权的依据。[^R04]

表格、筛选、弹窗和表单交由客户端组件处理。第一版默认：服务端读取最小用户上下文，列表数据由 TanStack Query 获取。只有明确改善首屏体验时才增加服务端预取和 HydrationBoundary，不同时让 RSC 与 Query 重复请求同一份数据。

### 5.4 Cache Components 使用纪律

公开数据可使用显式缓存及相应的生命周期、标签失效机制；用户 Session、权限判断、用户资料和私有业务记录不加入共享缓存。

请求时读取会话的组件按当前版本要求放在合适的动态边界 / Suspense 中。不在 Cache Components 模式中照搬旧教程的 `dynamic = 'force-dynamic'`、路由级 `revalidate` 等配置。[^R05]

## 7. 前端状态、UI 与交互规范

Ant Design 样式注册按官方 App Router 方案接入，并限制在需要它的认证和后台布局。验证首次加载、刷新、客户端跳转都没有无样式闪烁或 hydration mismatch。[^R07]

服务端数据由 TanStack Query 管理；筛选、分页、排序中需要可分享与浏览器回退恢复的部分写入 URL；表单输入由 Ant Design Form 管理；纯局部 UI 状态使用 React。第一版不引入 Redux 或 Zustand。

Query 按业务分别配置：开仓摘要、资产页及严格核验遵循第 1.4 节；复盘列表不因窗口聚焦、网络恢复或任务完成自动重新读取，外部取数与 AI 仍仅由用户主动发起。普通资料/设置查询才可采用 30 秒 `staleTime` 等通用初值；401、403 和参数错误不自动重试，写入及可能消耗模型费用/下载额度的请求不自动重放。

用户资料、设置和首次绑定查询按产品用户隔离；已有 Binance 业务的 Query Key 额外包含来源、绑定账户及绑定代次和筛选条件。本单、模板、偏好、草稿也按各自归属隔离，不要求尚未绑定用户提供不存在的绑定。登录身份确认后才加载对应本地状态，登出/身份变化清除可见数据和缓存并停止页面请求，迟到响应还须核对身份代次。退出后浏览器返回、跨标签退出、A 用户退出后 B 用户登录均应纳入测试。服务端预取使用请求隔离的 QueryClient，禁止模块级共享用户缓存。[^R08]

表格统一加载、空数据、错误与重试状态；提交按钮防重复点击，但服务端仍负责幂等与并发控制。保留原始时间点，交易显示、日期筛选、统计和导出统一使用北京时间 `Asia/Shanghai`；首版不提供改变业务日界线的 timezone 设置。

## 8. 后端分层、接口与错误协议

### 8.1 按模块所有权区分调用路径

以下为 Next 自己拥有的认证、资料和设置模块：

```text
客户端交互
  → Route Handler
  → 请求格式与来源检查
  → 输入校验
  → 会话及资源授权
  → Service
  → Prisma / 外部服务

Server Component
  → 会话及资源授权
  → 同一个 Service
  → Prisma / 外部服务
```

Server Component 不经 HTTP 调自己的 Route Handler。两条路径复用业务逻辑与访问控制，而不是绕过访问控制直查数据库。Next.js 官方建议服务端组件直接读取数据源，避免访问自身 HTTP 入口的额外往返。[^R09]

交易模块的路径为 `Route Handler / Server Component → 受保护业务服务入口 → 交易规则与事务 → Prisma / Binance / 模型`，大数据由浏览器受保护直连取得。这里访问独立业务服务是服务间调用，不是 Next HTTP 自调用；Next 不绕过业务服务直接读写交易表或自行发起 Binance 查询，图中的本地 Service 路径仅用于其自有认证/资料模块。

### 8.2 模块职责

Route Handler 保持薄：请求解析、Zod 校验、身份解析、调用所属业务入口、映射响应。模块所有者负责业务规则、权限策略和事务边界；简单模块可在自己的执行服务内直接使用 Prisma，不为了形式额外创建逐项转发的通用 Repository。常驻服务方案下，Next 中的交易调用封装只负责受保护的服务间请求，不复制交易规则或直接操作其表。

Actor 从可信 Session 解析，至少包含 userId 与账户状态。客户端传来的 userId、role、ownerUserId、emailVerified 一律不能作为授权依据。现有后台任务迁移时须保存可信发起用户与账户作用域，任务执行身份具有显式权限，不伪造普通用户绕过检查。

### 8.3 新增认证与设置接口提案

| 方法与路径                  | 职责                                         | 访问条件             |
| --------------------------- | -------------------------------------------- | -------------------- |
| `GET /api/v1/me`            | 当前用户公开资料 DTO                         | 有效用户             |
| `PATCH /api/v1/me`          | 修改允许的昵称等资料                         | 有效用户 + CSRF 检查 |
| `GET /api/v1/me/settings`   | 获取自己的设置                               | 有效用户             |
| `PATCH /api/v1/me/settings` | 修改已明确的非敏感偏好白名单；不修改业务时区 | 有效用户 + CSRF 检查 |
| `/api/auth/*`               | 注册、登录、验证、找回密码、会话管理         | Better Auth 原生协议 |
| `GET /api/health`           | 存活检查                                     | 无敏感信息           |
| `GET /api/ready`            | 数据库依赖探测                               | 监测系统授权         |

认证端点不包装成自定义统一 JSON，以免破坏 Better Auth 客户端协议。业务接口使用约定的成功与错误结构：

```json
{
  "data": { "id": "user-id", "name": "Display name" },
  "meta": { "requestId": "request-id" }
}
```

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "输入内容不符合要求",
    "fieldErrors": { "name": ["长度超出允许范围"] }

  "meta": { "requestId": "request-id" }
```

使用真实 HTTP 状态：401 未登录，403 操作无权限或账户停用，404 不存在或不应向当前用户暴露的资源，409 业务冲突，422 字段校验失败，429 限流，500 未预期错误，503 依赖不可用。不要全部返回 200。

## 9. 认证与会话架构

### 9.1 认证职责

Better Auth 负责凭证校验、密码哈希、邮箱验证、重置密码、Session 创建和撤销。认证库运行在应用服务端，数据库由 Prisma Adapter 接入 Neon。不同时接入 Neon Auth、Auth.js 或自写 JWT 登录作为另一套身份源。[^R10]

### 9.2 注册与验证

```text
填写邮箱和密码
  → 注册入口参数校验与限流
  → Better Auth 建立待验证账号
  → EmailService 调用 Resend
  → 页面提示验证邮箱，并提供受限流保护的重发入口
  → 用户打开验证链接
  → 验证邮箱
  → 用户正常登录
  → 创建 Session，进入后台
```

配置 `requireEmailVerification`；未验证用户不能进入业务后台。验证链接只完成邮箱验证，不在本方案中默认触发自动登录。邮箱已注册、找回密码与重发邮件的外部响应应尽量一致，降低枚举账户的风险。[^R11]

### 9.3 邮件失败不是数据库事务回滚

数据库创建用户与外部邮件发送不属于同一个原子事务。邮件调用失败后，账号可能已经存在但仍未验证，界面应允许通过受限流保护的重发流程恢复，不能诱导用户持续重新注册。

认证邮件在当前请求内等待邮件服务的接收结果，设置超时并记录失败。不使用未等待 Promise、`setTimeout` 或“请求结束后应该还能跑完”的假设发送关键邮件。服务商接受请求不等于邮件已送达。

对同一次发送尝试的网络重试使用同一幂等键；用户明确发起新的重发，应生成新的发送事件。Resend 提供幂等发送能力，正式发送前需要配置并验证发信域名。[^R12]

认证邮件第一版不实现自动补偿队列，用户可主动重发；这不取消已有归档和 AI 的持久任务与排队需求。若邮件将来要求无人值守重试或可靠通知，再设计 Outbox、幂等和补偿，不能声称普通异步函数等同可靠队列。

### 9.4 会话建议

| 配置                 | 本方案初值                                             |
| -------------------- | ------------------------------------------------------ |
| 存储                 | PostgreSQL 数据库 Session                              |
| Cookie               | HttpOnly、生产 Secure、SameSite=Lax、Host-only、Path=/ |
| 普通会话有效期       | 7 天滚动有效期                                         |
| 续期检查间隔         | 24 小时                                                |
| Session Cookie Cache | 第一版关闭，便于撤销及时生效                           |
| 高风险操作           | 最近重新认证；建议 15 分钟内完成的密码确认             |
| 密码重置             | 显式配置撤销其他 / 全部旧会话                          |
| 修改权限或停用账号   | 服务端即时检查账户状态，并撤销会话                     |

这些是建议配置，不是库的所有默认行为。Better Auth 支持会话有效期、续期和撤销；纯 RSC 读取不能承担 Cookie 刷新，客户端会话请求或相应 Route Handler 需按官方集成完成续期。[^R13]

生产和非生产必须使用不同认证 Secret。生产 trustedOrigins 使用精确生产域名；预览来源从部署系统控制的 URL 注入，不能信任任意 Host 请求头，更不能放行整个 `*.vercel.app`。

## 10. 授权与数据模型

### 10.1 授权矩阵

| 身份                 | 公开页面 |    本人资料 / 设置 | 其他用户数据 | 运营管理 |
| -------------------- | -------: | -----------------: | -----------: | -------: |
| 游客                 |     允许 |             不允许 |       不允许 |   不允许 |
| 未验证账号           |     允许 | 不允许进入业务后台 |       不允许 |   不允许 |
| 正常用户             |     允许 |               允许 |       不允许 |   不允许 |
| 已停用用户           |     允许 |             不允许 |       不允许 |   不允许 |
| 运营人员（未来扩展） |     允许 |             按策略 |     显式授权 | 专属权限 |

“登录成功”只完成认证；资源所有权与操作权限必须独立判断。默认拒绝，没有声明权限的操作不能因为已有登录态而放行。

### 10.2 认证表与业务表

| 表 / 模型                      | 职责                                    | 设计约束                                                                                           |
| ------------------------------ | --------------------------------------- | -------------------------------------------------------------------------------------------------- |
| User                           | 认证主体、基础资料                      | 核心字段由认证库约定；邮箱唯一性按库支持方式实现                                                   |
| Session                        | 可撤销登录会话                          | 用户关联、过期时间、库要求的唯一约束                                                               |
| Account（认证库）              | 密码凭证或外部登录身份关联              | 哈希与凭证由库管理；不是 Binance 账户，不保存 Binance Key                                          |
| Verification                   | 验证 / 重置流程记录                     | 按库协议设置有效期；定期清理过期记录                                                               |
| RateLimit                      | 数据库限流状态                          | 按当前库版本生成需要的结构                                                                         |
| UserSettings                   | 已明确的非敏感用户偏好                  | userId 唯一；交易业务时区固定北京时间                                                              |
| AuditLog                       | 关键安全与管理操作记录                  | 事件类型、actorId、对象、时间、requestId、最小必要详情                                             |
| BinanceBinding（目标概念）     | 产品用户与服务端确认 UID 的关联         | 不可复用的归属实例；每用户最多一个活跃绑定，归档也保留 UID 占位；状态、授权代次及注销释放遵循 10.5 |
| CredentialMetadata（目标概念） | 凭据类型、所属用户/绑定、版本及可用状态 | 保存密文和必要版本信息，主密钥独立保管；不与认证库 Account 混用                                    |
| TaskExecution（目标概念）      | 归档 / AI 执行权、排队、取消与检查点    | 关联可信所有者、账户及凭据版本，原子领取、租约和执行版本，不在任务载荷中复制密钥                   |
| 删除 / 撤销控制记录            | 用户、归属实例、凭据版本及失效代次      | 持久副本不随业务库恢复点回退，不包含密钥或交易内容；用于恢复时重放已确认决定                       |

现有交易领域继续覆盖 `trades`、`evidence`、`review_plans`、`review_verifications`、`history_raw`、`history_sync`、`account_archive`、`style_tags`、`review_notes`、`review_market`、`review_analysis`、`review_versions` 十二类记录，来源见 `src/review-backup.ts`；各自保存所属产品用户与原 Binance UID/来源，不能用网站 userId 替换交易所身份。目标概念表尚未生成 Prisma schema。

核心认证表以当前 Better Auth 配置生成的 schema 为起点，审阅后转为 Prisma migration，提交代码仓库。不要手写一套不同的 Session 表，再期待 Adapter 自动兼容。Better Auth 的 Prisma Adapter 支持生成 schema，实际数据库迁移由 Prisma 管理。[^R10]

账户 status 作为受保护扩展字段，默认 active；注册和资料更新输入不得修改 status、权限字段或 emailVerified。运营角色在真正启用运营模块时再增加，不提前建设通用 RBAC 表组。

### 10.3 新增业务资源时的强制规则

所有私有资源查询和修改均从可信 Actor 推导 ownerUserId。认证、个人资料、用户模型凭据及首次绑定按产品用户授权，允许尚无 Binance 绑定的已验证用户使用；已有 Binance 业务资源额外核对绑定、来源及原 UID，用户提供的资源 ID 或备份里的 UID 不构成授权。笔记、交易任务、行情、恢复预览和文件授权使用相同账户归属条件。索引围绕实际访问模式建立，现有每页 20 条及全筛选统计/导出范围保留，不能把分页限额套到全范围计算上。

写入事务只包含数据库操作，外部邮件和其他网络请求不放进长事务。涉及重复创建或外部副作用时，使用用户作用域的幂等键、数据库唯一约束和请求体摘要；同一键但不同请求内容返回冲突，不能仅靠按钮 disabled。

绑定前用用户提交的凭据在后端检查只读权限并读取 UID，再以事务和唯一约束完成归属确认；并发绑定同一 UID 只有一个成功，失败响应不泄露其他用户身份。更新同 UID 密钥不改变账本归属，不同 UID 不能通过更新字段把原历史改挂过去。金额与数量保持无损字符串及共享 BigInt 计算，ORM/JSON 不得中转成浮点数；PostgreSQL 写入须保留笔记版本条件、恢复预览复验和失败全量回滚。

### 10.4 托管凭据边界

已确认 Binance Key/Secret 由平台加密托管。凭据输入仅在当前表单和服务端必要处理期间存在，不回显或写浏览器持久存储；生产传输使用 HTTPS，禁用相关表单的日志、错误上报和录制。密码继续使用认证库哈希，外部 API 凭据则因签名/调用需要而采用可解密的认证加密；主密钥与密文分开保管，记录密钥版本并验证篡改/错用户解密失败。具体秘密管理产品待部署选择，不自行发明加密算法。[^R33]

第三轮已明确备份范围：用户下载的 JSON、CSV 及普通日志排除明文、密文和凭据引用；Neon 等平台受控灾备可包含密文，主密钥始终不进入数据库或业务备份。凭据密文与所有者、用途及版本绑定，错用户、篡改和旧版本不能解密或使用；平台持有的灾备副本遵守最长 30 天上限，密钥管理恢复与业务库恢复分别验证。

任务仅引用凭据版本，使用时重新确认可用性。凭据失效只停止对应外部能力，已有交易与报告保持可读；数据库恢复不能自动复活已撤销凭据或启动旧任务。平台解密主密钥的轮换、丢失和恢复必须有单独受控流程；不与认证 Secret 共用，也不因改登录密码而静默破坏全部用户凭据。

### 10.5 解绑、换账户与注销

“每人一个账户”指同时一个活跃绑定：解绑停止相关任务及外部读取并撤销平台保存凭据，原 UID 历史作为原用户的只读归档；允许绑定新 UID，新旧账本独立。保留历史期间保留原 UID 的所有者占位，同 UID 重绑重新验证凭据并增加授权代次，其他产品用户不能自助取得其归档。原用户重绑原 UID 可恢复原账本功能；注销后重新绑定则创建新的归属实例，不复用已删除实例。

注销要求最近重新认证，先提供导出机会，确认后立即停用登录、凭据和新任务，后台完成在线数据清理后才释放 UID 占位，新绑定不得继承旧数据。清理范围包括交易、笔记旧版本、AI 冻结快照/报告、临时文件与私有缓存；后台删除重试是维护任务，不触发 Binance 或模型调用。灾备最长 30 天到期并在恢复时重放删除/撤销决定，用户自行下载的备份不在平台可删除范围内。该上限已确认，所选资源的实际保留与清理仍须在上线前验证。

| 账户状态                   | 允许行为                                                                                      |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| 活跃绑定，凭据有效         | 按现行规格使用全部功能，外部取数和 AI 仍仅主动触发                                            |
| 活跃绑定，Binance Key 失效 | 停止对应 Binance 调用，原本地记录、笔记、统计及有独立有效模型 Key 的 AI 能力保留              |
| 已解绑归档                 | 原用户可查看历史、笔记、既有报告、统计并导出；不新增笔记、启动 AI、同步或恢复写入，重绑后恢复 |
| 注销清理中 / 已注销        | 拒绝用户数据访问和新业务任务，仅执行受控清理；不能凭相同 UID 复活旧数据                       |

完整功能等价验收针对活跃绑定；解绑后的只读限制来自本次已确认的生命周期选择，不能把 Key 临时失效等同于用户主动解绑。

### 10.6 用户自备模型密钥

费用归属已确认为用户自备 Key；首版继续当前 DeepSeek、`deepseek-v4-pro`、`high` 支持范围，不因自备 Key 增加任意模型端点或可由用户控制的外部 URL。平台不提供公共模型 Key 回退；没有用户 Key 时保留非 AI 功能与旧报告。不限调用次数不等于不限并发，排队及取消遵循第 3.3 节，token 用量不等同实际账单金额。

AI Key 长期加密托管，沿用 Binance 凭据的不回显、业务备份排除和受控密文灾备边界，以支持离开页面后继续及主动重试。更换或撤销模型 Key 停止后续调用，不得把未完成任务悄然改为使用新 Key；用户明确继续后才使用新版本。

### 10.7 备份归属与旧格式迁移

现有 JSON v1 仅包含来源和 Binance UID，不能区分注销前的原用户与后来同 UID 的新绑定。新导出采用带产品用户、不可复用归属实例和服务端归属证明的 v2 封装，保留现有业务记录、预览补缺及冲突版本规则；恢复仍须检查当前授权、来源、UID、归属实例和未被注销的状态，文件自报字段不作为授权。

旧 v1 包通过受控旧库迁移转换到明确的原用户/账户作用域，不作为公开恢复接口的永久跨用户兼容通道；当前本单的可信迁移另见 17.4。删除/释放后的旧归属包不能仅凭相同 UID 导入新账号。恢复到同一有效归属的 v2 备份保留完整恢复能力，恢复预览变化和并发业务写入仍须拒绝或重新预览。备份归属证明不将文件中的方案升级为可信当前本单。

## 11. 数据库连接、权限与迁移

### 11.1 连接方式

选择标准 TCP 驱动 `pg` 与 Prisma 的 `@prisma/adapter-pg`。本地连接 Docker PostgreSQL，生产连接 Neon pooled endpoint，确保环境差异主要在配置而不是业务代码。Neon 针对 Vercel Fluid compute 的文档推荐标准 Postgres TCP 驱动与连接池。[^R14]

| 用途       | 连接与凭据                                       |
| ---------- | ------------------------------------------------ |
| 应用运行时 | pooled endpoint + 最小权限 app role              |
| CI 迁移    | direct / unpooled endpoint + 独立 migration role |
| 开发与测试 | 本地或专用非生产数据库；不访问生产               |
| 运维恢复   | 独立受控管理员凭据，不放应用环境                 |

运行时仅有业务所需 DML 权限及必要序列权限，不拥有 DDL 或 schema owner 权限。Migration role 的凭据仅注入受保护迁移任务。表的现有授权与未来表的 default privileges 都要验证。

### 11.2 连接池纪律

每个运行实例复用 Prisma Client 与连接池；不在每个请求创建后立即断开，也不为每个请求生成一个永久池。第一版可从每实例最大 3 个数据库客户端连接开始，再按压测调整。实例数量 × 池大小是总体连接压力的重要因素；Neon pooler 不能替代应用侧并发控制。[^R15]

设置连接获取超时、闲置连接回收和查询预算，按 Vercel 生命周期处理暂停实例的空闲连接。数据库异常只对明确安全的只读请求或具备幂等保障的操作重试；不得对任意事务或写操作统一重试。

### 11.3 Prisma 版本一致性

本文使用 Prisma 7 工作流：`schema.prisma`、`prisma.config.ts`、`prisma generate`、`prisma migrate dev`、`prisma migrate deploy`。CLI、Client 和 driver adapter 使用匹配版本。配置同时明确 CLI 迁移连接与运行时 adapter 连接，不让二者意外指向不同环境。[^R03]

`prisma generate` 与普通应用构建不应要求生产 DDL 凭据。配置加载若默认读取迁移专用变量，应拆分命令配置或校验时机，而不是为方便构建把迁移凭据塞进应用 Functions。

## 12. 缓存、SEO 与性能边界

### 12.1 缓存矩阵

| 内容                     | 本方案缓存规则                               |
| ------------------------ | -------------------------------------------- |
| 内容随发布变化的官网页面 | 静态输出，随部署版本更新                     |
| 将来接入 CMS 的公开内容  | 显式公共缓存 + 按内容标签失效                |
| 用户菜单和会话结果       | 独立请求，私有响应 no-store                  |
| 认证 API                 | no-store，不进入公共 CDN 缓存                |
| 私有业务 JSON            | `Cache-Control: private, no-store`           |
| 后台个性化 HTML / RSC    | 不配置 public 或 s-maxage；核验平台实际响应  |
| 后台通用静态外壳         | 可作为无用户信息的静态部分输出               |
| hash 命名静态资源        | 交给框架与平台版本化缓存                     |
| 浏览器 Query 数据        | 仅当前身份上下文，登出清空，不持久化敏感数据 |

不要把全站 `/api/*` 配成公共缓存；也不要把“同域名”当成缓存可以混用的理由。用户授权检查不能因为某个页面已有缓存而跳过。

### 12.2 SEO 验收

首页原始 HTML 包含真实标题、主要正文和可抓取链接；每个公开页面有独立 title、description、规范链接与适当分享元数据。站点地图只收录公开且希望索引的页面。404 使用正确状态，不把所有错误重定向到首页并返回 200。

登录、注册、重置密码和后台设置 noindex。robots.txt 控制抓取，不是访问控制，也不能保证 URL 不被索引；后台真正依靠认证保护。不要同时阻止抓取又期待搜索引擎读取该页面的 noindex。[^R16]

预览与 staging 默认设置 `X-Robots-Tag: noindex, nofollow`，并启用部署访问保护；公开生产首页必须验收没有误带 noindex。canonical 与网站基础域名来自已验证环境配置，不从任意 Host 请求头构造。

第一版不引入 CMS。后续运营编辑确有需求时，再增加内容来源、发布 webhook、签名校验、缓存失效与回滚策略。

### 12.3 性能目标

| 指标             | 初始目标与测量条件                             |
| ---------------- | ---------------------------------------------- |
| 官网真实用户 LCP | P75 ≤ 2.5 秒                                   |
| 官网真实用户 INP | P75 ≤ 200 毫秒                                 |
| 官网真实用户 CLS | P75 ≤ 0.1                                      |
| 普通后台 API     | 目标地区、约定负载下，端到端 P95 ≤ 800 毫秒    |
| 登录请求         | P95 ≤ 2 秒；计入密码校验，不把邮件最终投递计入 |
| 后台常见交互     | 有即时状态反馈，不因数据获取冻结界面           |

前三项采用 Web Vitals 的良好体验阈值，其余为本方案目标。冷启动应单独标识并计入总体体验，不通过剔除慢请求制造达标。实际结果需在目标设备与网络条件下验证。[^R17]

## 13. 安全基线

### 13.1 输入、凭据与资源授权

所有业务请求服务端 Zod 校验；限制请求体大小、字段长度、页大小和排序字段白名单。Prisma 调用使用参数化方式；必要原生 SQL 不拼接用户输入。服务端只向浏览器返回显式 DTO，不直接序列化认证对象。

Cookie、密码、Session token、邮箱验证 token、重置链接、数据库 URL、Authorization 头、Binance Key/Secret、模型 Key、签名请求参数和敏感请求体均不进入生产日志。密钥不使用 `NEXT_PUBLIC_` 前缀，不提交到 Git。排错默认仅记录内部匿名标识、错误类别、时延和版本，不采集交易金额、笔记、模型输入或完整上游 URL。

### 13.2 自定义业务接口 CSRF 规则

Better Auth 的认证入口保留库原生来源与 CSRF 保护，不能将关闭检查作为修复跨域问题的手段。[^R18]

本方案自定义 JSON 写接口额外要求：

- 只允许所声明的 POST/PATCH/DELETE，GET 不修改业务状态。
- `Origin` 必须精确匹配当前环境的允许来源；缺失或不匹配时拒绝该浏览器会话写请求。
- 拒绝跨站 Fetch Metadata；Content-Type 必须为 application/json。
- 要求固定自定义请求头，例如 `X-App-Request: web`；不为任意跨域来源开放带凭据 CORS。

此处自定义头依靠浏览器同源与预检机制，不是秘密，不是身份凭据，也不能替代用户认证。将来增加 webhook 时，使用独立路径、签名和防重放规则，不通过开放这些 Cookie 接口来适配 webhook。OWASP 对基于自定义头、Origin 与 Fetch Metadata 的防护有相关指导。[^R19]

### 13.3 限流与防滥用

认证限流显式使用数据库共享存储，不依赖实例内存。Better Auth 官方指出默认内存存储不适合许多 Serverless 场景。[^R20]

初始策略建议：登录按 IP 与账户维度组合观察；例如每 IP 每分钟 20 次、同一账户失败尝试每 15 分钟 10 次；注册每 IP 每小时 10 次；邮件重发与找回密码每邮箱每 15 分钟 3 次。不要长时间硬锁整个账号，避免攻击者替他人制造拒绝服务。

这些是产品策略，不代表设置一个 Better Auth 选项即可覆盖所有维度。库原生端点限流与额外邮箱 / 业务配额应分别实现；对服务端直接调用的认证操作也必须检查是否经过限流入口。需要严格跨实例计数的自定义配额采用原子数据库操作，不能只把非原子计数搬到数据库。

数据库计数不是 DDoS 防护。配合平台入口规则；流量或攻击压力上升后再引入分布式限流存储与挑战机制。认证存储不可用时不得 fail-open。

### 13.4 安全响应头与 CSP

基线启用 `nosniff`、适当 Referrer-Policy、禁止嵌入后台页面的策略与 HTTPS。生产继续强制执行 CSP；新脚本/样式策略可额外用 Report-Only 观察，但不能替换已有强制保护。为 Next/React、样式注册及文件通道列出实际所需的最小来源并通过验收，不为兼容而放行任意内联脚本或任意连接。

不能不经验证就全站应用每请求 nonce：Next.js 的 nonce CSP 需要动态渲染，会与静态首页目标冲突。严格 nonce 仅在确认采用动态渲染的私有路由实施；公开路由使用经过验证的静态兼容策略。[^R21]

## 14. 环境隔离与配置

### 14.1 两个 Vercel Project、两个 Neon Project

| 环境       | Vercel                       | 数据库                           | 数据来源         |
| ---------- | ---------------------------- | -------------------------------- | ---------------- |
| Local      | 本地 Next.js                 | Docker PostgreSQL                | 合成 seed        |
| PR Preview | `product-nonprod` 的临时部署 | 非生产项目的独立 PR branch       | 合成基线数据     |
| Staging    | `product-nonprod` 的稳定域名 | 非生产项目的 staging/root branch | 合成集成测试数据 |
| Production | `product-prod`               | 独立生产 Neon Project 的主分支   | 真实生产数据     |

两套 Project 运行同一份代码，不是两套架构。生产 Project 禁止普通 PR 自动部署；非生产 Project 无生产数据库、生产邮件权限与生产认证 Secret。

Preview 分支从非生产合成数据基线创建，不从生产复制真实用户、密码凭证、Session 或个人资料。Neon 分支可以隔离变更，但分支复制本身不会自动脱敏。[^R22]

PR 关闭或分支删除后清理临时部署和数据库分支，同时设置定期清理兜底。正式环境与非生产使用不同邮件凭据和受控收件人策略。外部贡献者 PR 不自动获得云 API Key 或部署权限。

### 14.2 环境变量

| 变量                      | 用途                                   | 注入范围                      |
| ------------------------- | -------------------------------------- | ----------------------------- |
| `APP_ENV`                 | local / preview / staging / production | 构建与运行时                  |
| `APP_URL`                 | 当前环境规范来源和基础地址             | 构建与运行时                  |
| `DATABASE_URL`            | 应用 pooled 连接、最小权限角色         | 服务端运行时                  |
| `DATABASE_URL_UNPOOLED`   | migration role 的 direct 连接          | 受保护迁移任务                |
| `BETTER_AUTH_SECRET`      | 认证库 Secret                          | 服务端，环境隔离              |
| `BETTER_AUTH_URL`         | 认证 Base URL                          | 服务端，精确来源              |
| `RESEND_API_KEY`          | 事务邮件                               | 服务端；生产与测试分开        |
| `EMAIL_FROM`              | 已验证域名的发信地址                   | 服务端                        |
| `EMAIL_MODE`              | real / fake / allowlist                | 服务端；生产强制 real         |
| `VERCEL_TOKEN` 等部署凭据 | 发布                                   | GitHub Actions 受保护 Secrets |
| `NEON_API_KEY` 等管理凭据 | 非生产分支管理 / 生产管理              | 按项目权限与工作流隔离        |
| 部署保护 bypass secret    | CI 端到端访问受保护部署                | 仅 CI，不写入网页或公开日志   |

`NODE_ENV=production` 也会出现在预览构建；非生产 Project 的稳定部署在平台层也可能属于 Production 环境。因此索引、邮件、回调与业务开关必须以显式 `APP_ENV` 为准，而不能仅凭 NODE_ENV 或平台环境名。

环境变量变更只影响新部署，不自动改写已有部署。每次发布记录 commit SHA、APP_ENV、数据库分支标识和部署 ID，启动时校验环境组合，发现生产应用指向非生产数据库或反向混配立即失败。[^R23]

多用户版不再把全站共用的 Binance 或 `LLM_API_KEY` 环境变量作为用户凭据来源。各用户凭据遵循第 10.4、10.6 节，部署只配置获准服务使用的密钥管理引用、版本与服务间鉴权；具体配置名随选定部署方式定义。测试使用合成凭据与替换 transport，不从生产拉取用户密钥。常驻服务也纳入环境、版本、连接目标与密钥权限校验。

## 15. 本地开发与质量门禁

本地运行 Next.js，Docker Compose 只启动 PostgreSQL 等确实需要的依赖。数据库与生产保持相同主版本。邮件使用 fake adapter 或仅本地可见的测试收件机制，不将真实生产邮件 key 拉到每台开发机器。

计划提供这些脚本约定：

| 脚本                | 目标                                |
| ------------------- | ----------------------------------- |
| `dev`               | 本地应用开发                        |
| `lint`、`typecheck` | 静态检查                            |
| `test`              | 单元与组件测试                      |
| `test:integration`  | 真实 PostgreSQL 的接口 / 数据层测试 |
| `test:e2e`          | Playwright 关键流程                 |
| `db:generate`       | 生成 Prisma Client                  |
| `db:migrate:dev`    | 本地生成与验证迁移                  |

| `db:seed`           | 仅允许显式非生产环境的合成数据      |
| `build`             | 生产构建，不执行数据库结构修改      |

脚本名称属于实施约定，文档没有实际创建或运行这些命令。

首批测试优先覆盖授权、账户状态、Cookie、缓存隔离和数据库约束，不只追求组件覆盖率。必须至少有一次真实 Neon 非生产环境的连接和事务验证，不能只靠本地数据库通过就宣称生产兼容。

## 16. CI/CD、迁移与发布

### 16.1 单一发布入口

由 GitHub Actions 编排数据库分支、迁移、Vercel 部署与验证。关闭与此重复的 Git 自动生产发布，以及构建命令中的迁移逻辑。Neon/Vercel 托管集成可以作为以后简化手段，但同一资源不能同时由集成与自定义 CI 争相创建或迁移。

### 16.2 PR 流程

```text
可信 PR
  → pnpm frozen install
  → lint + typecheck + 单测
  → 真实 PostgreSQL 集成测试
  → 创建 / 复用该 PR 的非生产 Neon 分支
  → 应用本 PR 迁移，加载合成数据
  → 构建并部署 product-nonprod Preview
  → Playwright：认证、越权、SEO 与缓存测试
  → 全部门禁通过后允许合并
```

按 PR 和数据库分支设置并发组，避免同一分支同时运行迁移。外部 PR 先执行无 Secrets 的检查，只有受信任审批后才启动部署任务。不要在有 Secrets 的上下文执行未经审查的外部代码。

### 16.3 主分支与生产发布

```text
主分支 commit SHA
  → 非生产 staging 迁移、部署、回归
  → 生产受保护环境审批
  → 核验迁移兼容性与恢复窗口
  → 在生产执行已审阅的向后兼容迁移
  → 使用生产配置创建候选生产部署，暂不切换正式域名
  → 受保护地址上执行最小生产冒烟
  → Promote / 切换生产域名
  → 发布后监控与再次冒烟
```

**不直接把使用测试数据库、测试认证 Secret 构建的 Preview 改绑为生产。** 生产候选需要生产环境配置；验证的是同一 commit 的生产构建，而不是把测试运行环境带进生产。Vercel 支持暂不分配正式域名的生产候选及后续提升。[^R24]

候选生产部署的认证回调仍以正式 APP_URL 为准；跨 host 的完整认证回归在 staging 执行，生产候选只做不依赖回调的安全检查。正式域名切换后用专用测试账号完成认证冒烟，避免为了测试把任意候选域名加入长期可信来源。

### 16.4 数据库迁移规则

开发生成 migration 并审查 SQL；CI 只运行已提交的部署迁移。生产不使用 `db push` 或 `migrate dev`，不在函数冷启动时执行迁移。Prisma 7 提供通过 CI/CD 执行 `migrate deploy` 的工作流。[^R25]

采用扩展—迁移—收缩：先新增可兼容字段 / 表；部署兼容新旧数据的应用；分批回填并核验；经过回滚窗口后再删除旧字段。大表索引、约束变更和数据回填单独评估锁与执行时间，不视作普通小迁移。

迁移不是业务数据合并。PR 数据库分支上的测试记录不能作为生产数据“合并”回主库。

发布单元同时包含常驻业务服务的构建版本及数据库契约。滚动交接先停止领取新任务并处理执行租约，保留检查点，禁止旧实例越过执行版本写入；前端提升不能掩盖业务服务尚未升级。回滚必须验证网页、业务服务、数据库结构与凭据版本的兼容组合。

## 17. 回滚、备份与恢复

### 17.1 应用回滚

代码缺陷优先回退上一健康生产部署，前提是当前数据库结构仍兼容。Vercel 的部署回滚不会回滚数据库，而且旧部署会携带旧环境变量；密钥轮换、数据库切换之后不能盲目回滚到旧快照配置。[^R26]

回滚前确认：数据库兼容、认证 Secret 是否有效、邮件与第三方凭据是否仍有效、旧部署是否含已修复的安全问题。环境变更不兼容时，应基于旧代码重新构建新部署，而不是直接恢复旧部署。

### 17.2 数据库恢复

生产 Neon 主分支以至少 7 天的恢复历史窗口为初始方案，实际套餐与费用上线前确定，所有平台持有的可恢复业务副本最长不超过 30 天。把“启用了数据库”与“已经配置并验证恢复能力”视为两件事。[^R27]

发生数据误删或错误迁移时：停止相关写入；保全当前状态；恢复到隔离目标并核验时间点、记录数与关键关系；评估恢复后丢失的新写入；确认后切换；再恢复业务。不要未经核验直接覆盖现有生产库。

涉及认证表恢复时，必须考虑旧 Session、验证 token 与已撤销凭据被恢复的问题；默认强制失效旧会话与未消费验证 / 重置记录，并评估受影响账号是否需要重置密码。

用户凭据和删除记录采用同样的保守边界：恢复进入隔离维护状态，禁止 Binance、模型调用及用户数据访问；先从不随该业务库恢复点回退的持久控制记录重放撤销/删除决定，并增加恢复代次，令旧会话、直连授权和任务执行权失效。控制记录须在确认注销/撤销成功前可靠落地；仅放在会随整库一起回退的另一个表或 schema 不满足这一边界。

重放按原产品用户、不可复用的归属实例和凭据版本执行，不能只按 UID 删除而误伤后来的新用户。控制记录只保留必要内部身份与代次，不含交易、笔记或密钥；保留期覆盖全部尚可恢复副本及恢复验证过程。控制记录不可用或完整性不明时保持维护状态。若无法证明恢复凭据仍获授权，要求原用户重新提交；数据库与主密钥分别做恢复验证。

### 17.3 灾难恢复边界

本方案不是跨区域自动双活。Neon 的区域内高可用不能等同实时跨区域复制。需要应对供应商或区域级灾难时，增加定期加密逻辑备份到独立存储，并实际演练恢复到另一数据库。[^R28]

初始内部目标：一般逻辑故障 RPO ≤ 15 分钟、RTO ≤ 60 分钟；跨区域灾难如只依赖每日独立备份，最坏 RPO 可接近 24 小时，不能沿用前者目标。上述目标必须经实测认可，否则文档应记录真实恢复时间。

### 17.4 旧本地账本与当前本单迁移

先在隔离数据库演练，再在一次短暂停写窗口切换，不长期双写。旧库明确分配给原拥有者指定且验证了相同 Binance UID 的产品用户，不能以“最先注册”或导入文件中自报的 UID 自动认领。逐类比较记录数量、身份、金额字符串、净盈亏、方案关联、笔记版本和缺口状态；新系统开放写入前验收失败可撤销切换，继续使用旧服务。

首次需要保留的新系统写入发生后，旧 SQLite 只用于只读对账，禁止直接恢复可写。之后的故障优先回滚到兼容当前 Neon 的应用版本或进入维护状态，保全新增记录及撤销/删除决定；不声称旧库可随时无损回滚。平台持有的旧库、演练库、迁移导出和临时副本都进入最长 30 天清理清单，用户自己保管的本机原件由用户控制。

历史账本与当前本单分开迁移：JSON v1 不含旧 recovery 签名，通用备份导入也会将部分同步状态改为待重查，不能宣称完全保真。需要保留原状态时采用专用迁移路径，运行中的外部任务在切换时明确中断，已有分段/分页结果保留，继续由用户主动发起。

当前本单由一次本机迁移工具读取旧配置并校验原 recovery.v1，再通过受控迁移入口登记到已验证的新用户/UID 作用域，原预算和绝对止损不变；不把旧应用密码和旧验签配置长期放到公网服务。普通用户可编辑的备份文件不能升级成可信当前方案，缺少原 UID 的旧凭证也不能自动补造历史身份。迁移验收包含旧本单恢复后重新查询核验、错误 UID 拒绝及原始金额一致；无法建立可信关联时保留原工具完成该本单，不能重生成扩大预算。

浏览器中的旧无归属本单、模板和偏好由原用户明确迁移到新身份作用域；更换域名时提供受控迁移入口，不假设新站点能直接读取旧 origin 的 localStorage。真实停写、导入和切换仍需独立确认。

## 18. 监控、告警与运维责任

### 18.1 观测数据

| 维度     | 采集内容                                            |
| -------- | --------------------------------------------------- |
| 应用错误 | 浏览器异常、SSR 异常、API 未处理异常                |
| 请求     | requestId、route、method、status、duration、release |
| 认证     | 注册 / 登录成功率、失败原因分类、429 比例、邮件失败 |
| 数据库   | 连接等待、查询耗时、事务失败、存储和计算使用        |
| SEO      | 页面状态、公开 HTML、站点地图、误 noindex、抓取反馈 |
| 用户体验 | Web Vitals、后台接口与关键操作时延                  |
| 费用     | 计算、带宽、图片处理、数据库、历史存储、邮件        |

试运行只使用平台和服务端最小日志，不安装或配置 Sentry。凭据表单、交易内容、笔记、模型输入及会话录制均不采集；日志保留错误类型、时延、requestId 和版本等必要字段。以后新增第三方监控须单独明确范围，原稿 Sentry 资料只保留为参考，不构成首版依赖。[^R29]

### 18.2 初始告警建议

生产 5xx 在 5 分钟窗口超过 2% 且样本不少于 100 请求时告警；低流量情况下以连续探测失败补充。登录成功率异常下降、邮件持续失败、数据库连接获取失败和生产误带 noindex 单独告警。

就绪探测不对外暴露完整健康报告，不通过高频数据库探测无意保持非生产计算节点常开。可选监控故障不阻断应用；数据库故障不能放开鉴权；邮件故障不破坏官网与已有用户会话。

过期 Session、Verification、限流历史与孤立预览分支需要维护清理。第一版可使用独立的受保护定时 CI 作业，按批次执行幂等清理并记录结果；记录过期是否生效必须由请求时校验决定，不能依赖清理作业准点执行。审计日志先设 90 天的内部保留目标，再依据真实业务和隐私要求调整，不无限保留 IP 与个人信息。

明确三类责任人角色：发布负责人、事故响应负责人、数据恢复负责人。小团队可以是同一个人，但不能没有负责人；runbook 要记录控制台入口、权限取得方式与验证步骤，不记录明文密钥。

## 19. 成本与资源配置

用户仅确认小规模试运行，主要地区、人数和预算均未定，本节不是采购授权。按正式商业产品规划时应评估 Vercel Pro，不按 Hobby 可用于商业生产估算；Vercel 官方将 Hobby 限定为个人非商业用途，套餐之外仍需考虑用量与成员等成本。[^R30]

Neon 套餐与休眠设置须按选定恢复窗口、实际负载和预算决定。是否关闭生产 scale-to-zero 待测量冷启动后判断，不能将持续计费作为已批准默认；非生产优先休眠及计算上限。[^R31]

没有访问量、活跃时段、邮件量和数据库规模，本文不提供伪精确月账单。成本模型是：

```text
总成本 = Vercel 套餐与成员 + 计算 / 网络 / 图片等用量
       + Neon 计算 + 数据存储 + 历史窗口 + 分支资源
       + 常驻业务服务 + 必要出口 / 文件传输 + 凭据管理
       + 邮件 + 可选监控 + 域名 + 独立备份
```

用户模型调用费由用户向模型服务商承担，平台仍承担排队、处理和数据存储成本。月预算保持待定，不将旧稿每月 100 美元的示例当作承诺；上线前列出实际设施与费用估算，再确认预算及告警阈值。

## 20. 可选扩展及引入条件

| 需求出现时                                 | 新增模块                                 | 不改变的边界                                             |
| ------------------------------------------ | ---------------------------------------- | -------------------------------------------------------- |
| 运营人员管理全体用户                       | `/admin`、明确运营权限、MFA、审计        | 普通用户仍不能跨用户访问                                 |
| 团队 / 组织协作                            | Organization、Membership、邀请与租户授权 | 从服务端 Actor 推导租户，不能信任客户端 orgId            |
| 现有备份恢复之外的通用附件上传             | 按实际需求增加对象存储等设施             | 当前 64 MiB 恢复已属一期；所有文件传输仍需授权           |
| 既有归档 / AI 任务之外的定时导出与可靠通知 | 在一期任务执行方案上扩展                 | 幂等、超时、失败与任务状态；现有用户主动重试语义保持     |
| 运营编辑公开内容                           | CMS、签名发布 webhook、缓存失效          | 公开内容缓存与用户数据仍分开                             |
| 移动端 / 对外 API                          | OpenAPI、独立鉴权策略，必要时 NestJS     | 业务规则复用，避免两个后端同时拥有同一数据的写入规则     |
| 后端需要独立扩容和发布                     | NestJS 或其他独立业务服务                | Next.js 成为页面 / BFF，不继续绕过业务服务直写同一业务表 |

扩展以真实需求为触发条件，不以“以后可能用得到”为由提前堆叠依赖。当前函数运行环境的时长、持久存储与连接限制需要按平台文档评估；不能把普通请求处理器当常驻 Worker。[^R09]

## 21. 发布验收矩阵

| 类别         | 必须通过的验收                                                                                             |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| 官网         | 原始 HTML 有正文和元数据，正确 canonical，首页允许索引，404 正确                                           |
| 认证         | 注册、验证、登录、找回密码、重置、登出、撤销会话完整闭环                                                   |
| 账户状态     | 未验证 / 已停用账号不能读取后台数据；修改状态后访问即时受限                                                |
| 越权         | A 用户不能读写 B 用户资料、绑定、方案、账本、笔记、报告或文件；相同资源 ID 与伪造 UID 不能跨账户访问       |
| 客户端伪造   | role、status、emailVerified、ownerUserId 等输入不能提权                                                    |
| CSRF         | 跨站来源、缺少约定头、不合规内容类型的业务写请求被拒绝                                                     |
| 缓存         | A 登出 B 登录、浏览器返回、并行 SSR 请求均不泄露前一用户数据                                               |
| Cookie       | HTTPS、HttpOnly、Secure、SameSite、来源与生命周期符合配置                                                  |
| 邮件异常     | 邮件服务不可用时可恢复重发，不因重复注册生成异常状态                                                       |
| 依赖故障     | 数据库故障返回可观测错误，不绕过鉴权、不错误清除会话                                                       |
| 环境         | Preview 无生产数据 / Secret，不可向任意真实收件人发邮件                                                    |
| 构建         | 官网没有加载后台核心依赖；样式无闪烁；没有 hydration mismatch                                              |
| 数据库       | 真实 Neon 连接、事务、唯一约束、迁移与权限均验证                                                           |
| 发布         | 迁移先验证，生产候选使用生产配置，域名切换受控                                                             |
| 恢复         | 上一版本应用回滚、隔离数据库恢复、旧凭据检查至少各演练一次                                                 |
| 日志         | requestId 可追踪，错误可定位，敏感数据不出现在日志 / 监控                                                  |
| 性能         | 按明确设备、地区、负载条件测量，不以开发环境响应替代                                                       |
| 绑定与密钥   | 同 UID 并发绑定只有一个成功；同 UID 换 Key 保留历史、不同 UID 不改挂历史；明文/密文不从 DTO 或业务备份泄露 |
| 私有读取协调 | 两用户并发读取同一接口不共享签名、响应或权限错误；同出口的额度与冷却协调有效                               |
| 任务         | 排队公平、取消及实例交接不会重复收费调用；密钥变更不静默改用新 Key；登出不丢失已授权任务                   |
| 业务回归     | 开仓计算与恢复、资产刷新、订单/周期、笔记、统计、行情、单笔/批量 AI、CSV / JSON 恢复均按现行测试验收       |
| 文件与恢复   | 64 MiB 通道、跨用户文件拒绝、过期预览拒绝、在线任务写入互斥、失败回滚和旧版本保留                          |
| 迁移         | 旧库归属明确、金额与统计可对账、旧本单可信恢复；模拟/真实隔离，跨域浏览器状态迁移可验证                    |
| 大 JSON      | 超过普通函数体积限制的合成 AI / 统计 / 证据可完整获取；摘要、分页和直连不改变分析或统计范围                |
| 注销与再绑定 | 归档只读、Key 失效与解绑有别；注销清理含旧版本/冻结快照，释放 UID 后不继承原数据，旧归属备份不得复活       |
| 灾备控制     | 恢复点之外的删除/撤销记录可重放；控制记录缺失时拒绝上线，恢复不误伤同 UID 的后来绑定；全部副本到期清理     |

## 22. 实施顺序与交付物

完整执行顺序、关联文件、每阶段验收及授权边界集中维护在[重构实施计划](refactor-implementation-plan.md)，等待用户最终确认后开始。顺序为：基线与身份入口 → 归属/密钥/PostgreSQL 账本 → 业务执行与数据通道 → React 等价迁移与官网 → 隔离迁移/恢复及本地完整交付 → 获授权的外部验证与试运行切换。

阶段 1–5 可在本地与合成数据上完成；阶段 6 前再确定地区、预算及资源，采购、真实迁移和生产部署分别确认。首版交付包含全部现有业务和新增用户边界，官网和认证通过不等于重构完成；本文件不作工期承诺或已通过声明。
